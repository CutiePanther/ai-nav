## 核心概念

缓存（Redis）与数据库（MySQL）是两套存储，写入时先写谁、何时失效都可能导致**缓存与库不一致**。目标是尽可能降低不一致窗口，最终达到**最终一致**。

## 常见读写策略

- **旁路缓存（Cache Aside）**：
  - 读：先读缓存，未命中则读库并回填缓存；
  - 写：**先更新数据库，再删除缓存**（延迟失效，被动重建），比先写缓存出错更少；
- **先删缓存再更新库**：在两次请求并发时极易产生旧值回填，一般避免；
- **延时双删**：更新 DB 后删缓存，等待短暂时间（约 100ms）后再删一次，兜底并发场景下「旧读回填」；
- **删除 vs 更新缓存**：写入后通常**删**缓存而非写缓存，让下一次读再去加载最新值，避免写复杂对象序列化开销与中间态。

## 为什么仍有窗口期

- 并发读请求在「DB 更新完成、缓存删除前」仍能读到旧缓存，存在毫秒级不一致；
- Redis 自身**缓存穿透/击穿**会放大问题，需配合互斥锁、过期时间错峰处理。

## 面试加分点 / 追问方向

- **能否做到强一致**：缓存与 DB 通常只能最终一致，强一致需引入分布式事务或队列，成本高；
- **分布式锁**：更新 DB 与删缓存之间可用 Redis 分布式锁串行化，降低并发窗口，但要注意锁的租约与节点故障；
- **消息队列补偿**：删缓存失败时，可投递 MQ 由消费者重试删除，作为可靠兜底；
- **内存缓存 vs 数据库缓存**：与本地缓存（如 Caffeine）+ 异步刷新做对比。
