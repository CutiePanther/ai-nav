## 为什么叫"窗口"

模型在生成每个 token 时，只能"看到"输入里有限的 token，就像透过一扇滑动窗口看序列，看不了全量。这个窗口大小即 **context length**（单位：token，而非字数或字符数）。

## 一次调用能放多少内容

模型可处理的内容 = **输入 + 输出 ≤ 上下文窗口**。例如窗口 128K 的模型：

- 一段 80K token 的长文档 + 问题（约 1K）后，剩余留给生成本轮输出的上限就只剩约 47K；
- 多轮对话会把历史消息也算进输入，越聊占的窗口越多，超出即被截断。

## 为什么厂商疯狂堆窗口

窗口越大，就能越直接地处理**长文档问答、整库代码、超长对话**，甚至是"把整本书/整个代码库塞进去"的玩法；窗口也是衡量模型档位的重要参数（如 4K / 32K / 128K / 1M 常见档位）。

## 代价与取舍

不是越大越好，需要折中：

- **开销**：注意力与缓存随序列长度上升，窗口过大显著推高首 token 延迟与推理成本；
- **"中间迷失"**：即便窗口装得下，模型对位于长序列中部的信息注意力往往衰减，仍需靠 RAG 或检索定位关键片段而非"全塞给模型"；
- **工程策略**：用滑动窗口、摘要压缩历史、或结合 RAG 只保留相关片段，是控制上下文占用与成本的常用手段。

## 面试加分点

- token ≠ 字数：中文大致 1 字 ≈ 1～2 token，英文约 3.5~4 字符 ≈ 1 token；
- RoPE / 相对位置编码与窗口外推（如 YaRN）常用来让模型"超越"训练窗口；
- 提到"上下文工程（Context Engineering）"：与其盲目扩窗，不如系统控制输入质量与长度。
