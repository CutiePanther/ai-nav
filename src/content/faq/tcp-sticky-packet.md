## 为什么会出现粘包/半包

TCP 是**面向字节流**的协议，发送方 `send` 的数据只是拷贝进内核缓冲区，真正何时发送、如何切分报文由滑动窗口、拥塞窗口和缓冲区大小决定。因此：

- **粘包**：多个用户消息被合并同一个 TCP 报文里，接收方一次读到多段不完整消息；
- **半包（拆包）**：一个完整用户消息被拆成多个 TCP 报文，接收方可能只读到其中一部分。

这正是 TCP 与 UDP 的本质差异：UDP 是面向报文、边界清晰的，而 TCP 没有边界。

## 解决方案（在应用层定义边界）

- **固定长度消息**：约定每个消息都是 N 字节，接收端攒满 N 字节即视为一个完整消息；
- **特殊分隔符**：在消息间插入特殊字符（如 HTTP 用 `\r\n\r\n`）作为边界，需注意对内容里的分隔符做转义；
- **自定义消息头**：包头固定大小并携带长度字段（如前 4 字节表示 payload 长度），接收端先读包头、再按长度读数据。

## 面试加分点 / 追问方向

- **粘包 vs 半包**：严格来说「半包」是拆包导致，两者统称为流式边界问题，面试要分清楚两种现象；
- **长短连接与粘包概率**：TCP 维持长连接并连续发送小消息时，粘包概率更高；
- **Netty / 序列化框架**：很多框架已内置长度字段，如 Netty 的 `LengthFieldBasedFrameDecoder`，可借此说明工程实践。
