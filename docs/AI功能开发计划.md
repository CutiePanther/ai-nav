# AI 能力开发计划

> 适用项目：`ai-dev-nav`（Astro 7 纯静态站）
> 文档版本：v1.1 · 2026-09-03
> 目标：把站点从「静态内容仓库」升级为「可对话的 AI 学习教练」

---

## 0. 结论先行

**一句话路线**：保留静态主站不动，AI 能力做成**独立的边缘 API 服务**，前端用 fetch 调用。分 3 期主功能 + 1 期待定落地，**第一期（AI 学习助手）5 个工作日可上线**。

**三个必须先解决的前提**（否则 AI 功能无从谈起）：

| # | 前提 | 现状 | 必须动作 |
|---|------|------|----------|
| 1 | 服务端 | 纯静态，部署在 GitHub Pages，无运行时 | 引入独立 API 服务（不改造主站架构） |
| 2 | 密钥安全 | 无 | API Key 只能存在于服务端，前端永不接触 |
| 3 | 可检索的知识结构 | 内容在 markdown 里，Pagefind 只有关键词索引 | 构建期切片 → 嵌入 → 向量索引 |

**优先级判断**：先做 `AI 学习助手（站内 RAG 问答）`，这是唯一能立刻把 204 条存量内容「盘活」的能力；再做 `面试教练`（差异化最强，别人抄不走）；`AI 资讯日报`排第三（最轻，复用 RSS 管道）；语义搜索和内容自动生产**暂缓**——前者 Pagefind 已够用，后者会降低内容质量。

**砍掉个性化路线生成**（本次决策）：投入产出比不划算——路线内容只有 5 条，所谓「定制」的边际价值有限，却要额外引入「表单收集 + 结构化生成」两处复杂度。路线数据仍会进知识库，但只用于让 AI 助手回答「怎么学、学习路径」类问题，不做「按用户背景生成定制路线」的交互功能。

## 一、现状诊断

### 1.1 内容资产盘点

| 集合 | 数量 | 形态 | AI 可用性 |
|------|------|------|-----------|
| `faq` 面试题 | 114 | 结构化 markdown（含 answer/refs/tags） | ⭐⭐⭐⭐⭐ 核心知识库 |
| `docs` 官方文档导航 | 22 | 外链 + 简介（**无正文**） | ⭐⭐ 只能做导航推荐 |
| `tools` AI 工具 | 30 | 外链 + 一句话简介 | ⭐⭐ 只能做工具推荐 |
| `info` 资讯 | 38 | 外链 + 摘要 | ⭐⭐⭐ 可做日报/摘要 |
| `roadmaps` 学习路线 | 5 | TS 数据，含阶段/tasks/checkpoint | ⭐⭐⭐⭐ 回答「怎么学」类问题 |

**关键发现**：真正有"知识密度"、值得做 RAG 的只有 `faq`（114 题）和 `roadmaps`（5 条）。`docs`/`tools` 是外链卡片，没有正文，硬塞进向量库只会污染检索结果。

### 1.2 技术现状

- Astro 7 + Tailwind v4 + Pagefind（关键词搜索）+ `prebuild` RSS 抓取
- 输出 `output: static`，部署在 GitHub Pages / Vercel / Cloudflare Pages
- 依赖极简：`astro` / `tailwindcss` / `pagefind` / `rss-parser`
- 无用户系统、无数据库、无埋点

### 1.3 硬约束

> **GitHub Pages 不提供任何服务端运行时。** 一旦需要 AI，就必须二选一：
> - **A. 主站改 SSR**（加 adapter，换部署平台）—— 改动大，SEO/构建链路全受影响；
> - **B. AI 独立成服务**（推荐）—— 主站继续静态部署，AI 走跨域 API，失败自动降级，**改动最小、风险最低**。

**明确建议走 B。**

## 二、AI 功能候选池与优先级裁决

| ID | 功能 | 用户价值 | 实现难度 | 边际成本 | 裁决 | 期次 |
|----|------|----------|----------|----------|------|------|
| A | **站内 AI 学习助手**（RAG 问答，带引用） | ⭐⭐⭐⭐⭐ | 中 | 低 | ✅ **做，最高优先** | P1 |
| B | **AI 面试教练**（连续追问 + 回答评分） | ⭐⭐⭐⭐⭐ | 中 | 中 | ✅ **做，差异化核心** | P2 |
| D | AI 资讯日报 / 摘要 | ⭐⭐⭐ | 低 | 低 | ✅ 做（复用 RSS 管道） | P3 |
| G | 工具/文档智能推荐 | ⭐⭐ | 低 | 极低 | 🔶 塞进 A 一起做 | P1.5 |
| C | ~~个性化学习路线生成~~ | ~~⭐⭐⭐⭐~~ | ~~中~~ | ~~中~~ | ❌ **砍掉**（ROI 不足） | — |
| E | 语义搜索（替代 Pagefind） | ⭐⭐ | 中 | 中 | ⏸ **暂缓**，Pagefind 已够用 | — |
| F | AI 批量生产题目/答案 | ⭐⭐ | 低 | 低 | ⏸ **暂缓**，易稀释内容质量 | — |

**砍掉/延后的理由**：
- **C 个性化路线生成**：路线内容只有 5 条，「定制」的边际价值有限；却要额外引入表单交互 + 结构化生成两处复杂度。路线数据仍进知识库，让 AI 助手回答「怎么学」类问题即可。
- **E 语义搜索**：114 题规模下，关键词搜索 + 分类筛选已经够准，上向量搜索收益不明确，且有检索延迟成本。等题库过 500 题再考虑。
- **F 内容自动生产**：AI 生成的面试题答案质量不可控，一旦放进题库会毁掉当前"详答、可信"的口碑。要做也只能做「人工审核后入库」的半自动流水线，那是运营工具不是用户功能。

## 三、目标架构

### 3.1 分层设计

```
┌────────────────────────────────────────────────────────┐
│  交互层  Astro 静态页 + 客户端 JS（SSE 流式渲染）         │
│  · 悬浮 AI 助手入口  · 题目页「追问」                     │
└───────────────────────┬────────────────────────────────┘
                        │ HTTPS + SSE（跨域，需 CORS）
┌───────────────────────▼────────────────────────────────┐
│  服务层  AI API（Cloudflare Workers / 轻量 Node）        │
│  · /api/chat      问答（RAG + 流式）                     │
│  · /api/interview 面试教练（多轮状态机）                  │
│  · 中间件：鉴权 / 限流 / 缓存 / 审计日志                  │
└──────┬──────────────────────┬──────────────────────────┘
       │                      │
┌──────▼──────────┐  ┌────────▼─────────────────────────┐
│  索引层          │  │  模型层                            │
│  向量库 + 原文表 │  │  LLM（对话/评分）                  │
│  构建期生成      │  │  Embedding（切片向量化）            │
└──────▲──────────┘  └───────────────────────────────────┘
       │
┌──────┴─────────────────────────────────────────────────┐
│  内容层  src/content/**.md + src/data/roadmaps.ts        │
│  → 构建期脚本切片/嵌入/写索引（npm run build:index）      │
└────────────────────────────────────────────────────────┘
```

### 3.2 部署路线对比

| 方案 | 组成 | 优点 | 缺点 | 推荐度 |
|------|------|------|------|--------|
| **① CF 全家桶** | Workers + Vectorize + KV + Workers AI | 免费额度对个人站绰绰有余；零运维；全球边缘低延迟 | 绑定 Cloudflare 生态；国内直连不稳 | ⭐⭐⭐⭐ **主推** |
| **② 自托管 Node** | 轻量云主机 + SQLite(sqlite-vec) + PM2 | 完全自控；国内访问快；无厂商锁定 | 要运维；月付服务器费 | ⭐⭐⭐⭐ **国内用户主推** |
| ③ Vercel + Upstash | Serverless Fn + Vector + Redis | 与现有 Vercel 部署一致 | 免费额度偏紧；国内访问一般 | ⭐⭐⭐ |
| ④ 主站改 SSR | Astro adapter | 一体 | 破坏现有静态部署链路 | ⭐ **不推荐** |

> **决策建议**：如果你的用户主要在国内，**选 ②**（轻量云主机 2C2G 足够，月成本几十元，且 API 响应快）；如果目标是海外/全球访问，**选 ①**。两者 API 契约完全一致，可随时切换，**先按 ① 的免费额度做原型，跑通后再按用户分布决定落地**。

## 四、技术选型

| 环节 | 选型 | 理由 |
|------|------|------|
| 对话 LLM | **DeepSeek-chat** 主力；通义千问 / GLM 备选 | 中文技术语境好、价格低、有 OpenAI 兼容接口，换模型只改 baseURL |
| 评分/结构化输出 | 同上，开启 JSON Mode | 面试评分需要稳定结构化返回 |
| Embedding | **BAAI/bge-m3**（自托管，1024 维）或云 API `text-embedding-v3` | bge-m3 中文检索效果好、支持长文本；云 API 省事但每次重建索引要付费调 API |
| 向量库 | sqlite-vec（自托管）/ Vectorize（CF） | 数据量仅数百条，`sqlite-vec` 单文件足够，无需上重型库 |
| 检索策略 | **BM25 + 向量 混合检索（RRF 融合）**，暂不引 Rerank | 114 题规模下 Rerank 收益 < 15%，却多一次模型调用；后期可加 |
| 流式 | **SSE**（`ReadableStream` + `text/event-stream`） | 比 WebSocket 简单，Astro/Workers 原生支持，够用 |
| 缓存 | KV / 内存 LRU：相同问题 24h 复用 | 高频问题（如"什么是 RAG"）直接命中缓存，成本降到近零 |
| 限流 | IP 维度令牌桶：10 次/分钟、100 次/天（未登录） | 防刷、控成本的第一道闸门 |

## 五、分阶段实施计划

> 总工时：P0 3 天 + P1 5 天 + P2 5 天 + P3 2 天 = **约 15 个工作日**（去路线生成后比原 20 天节省 5 天）。

### P0 · 地基（3 个工作日）

**目标**：跑通「静态站 → 跨域 API → 流式输出」全链路，密钥不落地到前端。

| 任务 | 说明 |
|------|------|
| 建 `ai-service/` 独立目录 | 与 Astro 主站解耦，可单独部署；Node + Hono（轻量、Workers 兼容） |
| 环境变量与密钥管理 | `.env` 本地 / 平台 Secrets 线上，**绝不进 git**；`.gitignore` 加 `.env*` |
| 健康检查 + CORS | `GET /api/health`；CORS 白名单只允许主站域名 |
| 前端 `useAI()` 客户端封装 | 封装 SSE 解析、超时、错误降级（API 挂了 → 隐藏 AI 入口，站点照常可用） |

**验收**：本地起服务，`curl` 能拿到流式 token；主站调用失败时页面无任何报错、AI 入口自动隐藏。

### P1 · AI 学习助手（5 个工作日）⭐ 核心

**目标**：用户问任何 AI 学习相关的问题，基于站内 114 题 + 5 条路线作答，**每条结论都能点回原题**。

| 任务 | 说明 |
|------|------|
| ① 索引管道 `scripts/build-index.mjs` | 读 `faq/*.md` + `roadmaps.ts` → 按语义切片（单题 = 1 chunk；路线按阶段切）→ 调 embedding → 写 `ai-service/data/index.db` |
| ② 混合检索 `retrieve()` | BM25（自建倒排，纯 JS 百行内）+ 向量检索 → RRF 融合 → Top-5 |
| ③ `/api/chat` SSE 接口 | 拼 Prompt（系统人设 + Top-5 上下文 + 用户问题）→ 流式返回 |
| ④ 引用机制 | 要求模型在句中标注 `[ref:1]`，前端渲染成可点击卡片，跳到 `/faq/xxx` |
| ⑤ 相关推荐 | 回答末尾附「延伸阅读」3 条（G 功能，顺手做） |
| ⑥ 反馈按钮 | 👍/👎 写入日志，作为后续优化语料 |

**Prompt 骨架**（v1，需实测调优）：

```
你是 ai-dev-nav 的 AI 学习助手，只回答 AI/机器学习/大模型/工程相关的问题。

规则：
1. 只能使用 <context> 中提供的站内内容作答，禁止引入外部知识。
2. 每个事实性结论后用 [ref:N] 标注来源编号，N 对应 context 中的编号。
3. context 中没有的内容，直接回答「站内暂无这块内容」，不要编造。
4. 回答用中文，结构化（分点/小标题），控制在 400 字内，除非用户要求展开。
5. 用户问题若与 AI 学习无关，礼貌拒绝并引导回站内栏目。

<context>
[1] 标题：... 分类：... 正文：...
[2] ...
</context>

用户问题：{{question}}
```

**验收标准**：
- 20 条测试问题（覆盖 6 个分类）中，**引用准确率 ≥ 90%**（人工核对 ref 是否真的支持该结论）
- 首 token 延迟 < 1.5s，完整回答 < 8s
- 幻觉测试：问 5 道站内不存在的问题，必须全部回答"暂无"
- 主站构建时间增加 < 2min（索引放到独立命令，不阻塞 `npm run build`）

### P2 · AI 面试教练（5 个工作日）⭐ 差异化

**目标**：选一道题 → AI 当面试官，你口述回答 → AI 追问 2-3 轮 → 出评分报告。这是纯导航站完全做不了的能力。

| 任务 | 说明 |
|------|------|
| ① 会话状态机 | `sessionId` + 轮次状态（提问 → 作答 → 追问 → 结束），存 KV/SQLite，TTL 30min |
| ② 面试官 Prompt | 基于题目 `answer` 字段生成追问（挖深度、挖边界、挖工程落地） |
| ③ 评分维度 | 准确性 40% / 完整性 30% / 表达清晰度 20% / 工程实践 10%，JSON Mode 输出 |
| ④ 报告页 | 雷达图（纯 SVG，不引图表库）+ 逐轮点评 + 「标准答案」对照 + 薄弱知识点链接 |
| ⑤ 错题本 | localStorage 存 sessionId 列表，可回看历史报告 |

**验收**：同一份回答，两次评分波动 ≤ 1 分（5 分制）；追问不重复、不偏离题目。

### P3 · AI 资讯日报（2 个工作日）

**目标**：把每日新增的 RSS 资讯自动聚类、摘要，生成站内可读的「AI 日报」栏目，成为站点持续更新的内容来源。

| 任务 | 说明 |
|------|------|
| ① 每日聚合脚本 | 复用 `fetch-rss.mjs` 的抓取结果，把当日新增条目送 LLM 做聚类 + 摘要 |
| ② 内容落地 | 生成 `src/content/daily/YYYY-MM-DD.md`（结构化：分类 + 条目 + 一句话摘要 + 外链） |
| ③ 前端栏目 | 新增「AI 日报」列表页 + 详情页，复用现有 info 页模板 |
| ④ 定时触发 | 接入自动化调度（GitHub Actions cron / 平台定时任务）每日构建期运行 |

**验收**：日报单期生成成本 < 0.1 元；生成的 markdown 100% 符合 content collection schema，能正常被 Astro 构建收录。

## 六、关键设计细节

### 6.1 索引管道设计（概览）

```js
// scripts/build-index.mjs 核心流程
1. loadContent()    // faq: 114 篇 → { id, title, category, difficulty, body, tags }
                    // roadmaps: 5 条 → 按 stage 拆成 N 个 chunk（用于回答「怎么学」）
2. chunk()          // 单题超 1200 字才二次切分（按 ## 小节切），绝大多数 1 题 1 chunk
3. embed()          // 批量调 embedding，100 条/批，失败重试 3 次，结果落盘缓存
4. upsert()         // 写 sqlite：vectors(vec) + chunks(id, docId, title, text, meta)
5. verify()         // 抽样 5 条做检索回归，确认 Top-3 命中原题
```

**增量更新**：记录每个文件的 mtime，只重建变更文件的 chunk。全量重建一次约 1-2 分钟（114 题 + 路线，约 350 chunk）。

#### 6.1.1 知识库边界：哪些进、哪些不进

| 内容 | 进知识库？ | 理由 |
|------|-----------|------|
| `faq` 114 题 | ✅ 进 | 有正文 + 答案，唯一高密度知识源 |
| `roadmaps` 5 条 | ✅ 进（按阶段切） | 回答「怎么学/学习路径」类问题 |
| `docs` 22 条 | ❌ 不进 | 只有外链 + 简介，无正文，是噪声 |
| `tools` 30 条 | ❌ 不进 | 同上，只做外链卡片 |
| `info` 38 条 | ❌ 不进知识库 | 走独立「日报」管道 |

**原则：知识库只放「有正文、能回答问题」的内容，外链卡片一律不进**——否则 AI 会拿一句简介当知识去回答，幻觉率飙升。

#### 6.1.2 切片结构

faq：1 题 = 1 chunk（title + answer + 正文全文拼成 text）：

```jsonc
{
  "id": "faq-attention-mechanism",
  "type": "faq",
  "title": "注意力机制解决了什么问题？",
  "category": "深度学习",
  "difficulty": "进阶",
  "text": "注意力机制解决了什么问题？……（title+answer+正文）",
  "url": "/faq/attention-mechanism",
  "mtime": 1725000000
}
```

roadmaps：1 个 stage = 1 chunk（name + desc + skills + tasks + checkpoint + project 拼接）。仅当单 chunk 超 1200 字才按 `##` 小节二次切分。

#### 6.1.3 向量化

| 模型 | 维度 | 最大长度 | 部署 | 判断 |
|------|------|----------|------|------|
| **BAAI/bge-m3** | 1024 | 8192 | 自托管（CPU 可跑） | ⭐ 首选，中文好、开源零成本 |
| BAAI/bge-large-zh-v1.5 | 1024 | 512 | 自托管 | 备选，纯中文但长度受限 |
| 通义 text-embedding-v3 | 1024 | 8192 | 云 API | 备选，省运维但付费 |

要点：100 条/批、失败重试 3 次；**向量做 L2 归一化**（点积才等于余弦）；**待向量化文本里带上标题**（否则标题信息丢失降召回）。

#### 6.1.4 存储 schema

```sql
CREATE TABLE chunks (
  id         TEXT PRIMARY KEY,
  type       TEXT NOT NULL,
  title      TEXT NOT NULL,
  category   TEXT,
  difficulty TEXT,
  text       TEXT NOT NULL,
  url        TEXT NOT NULL,
  mtime      INTEGER
);

CREATE VIRTUAL TABLE chunk_vectors USING vec0(
  chunk_id  TEXT PRIMARY KEY,
  embedding FLOAT[1024]
);
```

BM25 倒排不进数据库：构建期生成 `Map<term, Array<{chunkId, tf}>>`，序列化 JSON 存文件，服务启动时加载进内存（350 chunk 的倒排仅几 KB）。

#### 6.1.5 构建与增量更新

```
loadContent() → 读 faq/*.md + roadmaps.ts，解析成 chunk[]
diff()         → 对比每个文件 mtime，只处理「新增/修改」的 chunk
chunk()        → 超 1200 字才二次切分
embed()        → 批量向量化 + 归一化（只算 diff 出来的）
upsert()       → 写 chunks + chunk_vectors + 重建倒排
verify()       → 抽样 5 题，检查 Top-3 是否命中原题
```

回归验证不可省：防「索引悄悄坏了但没人知道」。

#### 6.1.6 查询侧

```
用户问题
  ├─ 向量化（同一 embedding 模型）→ 余弦 Top-10
  ├─ 分词 → BM25 倒排 Top-10
  └─ RRF 融合：score = Σ 1/(60 + rank) → 去重取 Top-5 → 拼进 <context>
```

两条路都走的原因：`GQA`/`LoRA`/`vLLM` 等缩写纯向量召回差，BM25 精确命中补上。

### 6.2 检索策略

```
用户问题
  ├─ 向量检索  → Top-10  (语义相近)
  ├─ BM25      → Top-10  (关键词精确命中，如 "GQA" "FlashAttention")
  └─ RRF 融合  → Top-5   → 送入 LLM
```

**为什么必须混合**：纯向量检索对 `GQA`、`LoRA`、`vLLM` 这类缩写词和专有名词召回很差，BM25 正好补上。这是 RAG 里性价比最高的一次优化。

### 6.3 成本控制（三道闸门）

| 闸门 | 措施 | 效果 |
|------|------|------|
| 前端 | 输入限长 500 字；禁用连续发送；展示「本次消耗」提示 | 阻断误操作 |
| 网关 | IP 限流 10/min、100/day；相同问题 KV 缓存 24h | 阻断刷量，高频问题零成本 |
| 模型 | 上下文只送 Top-5（约 2k token）；`max_tokens=800`；temperature=0.3 | 单次成本可控 |

**成本量级估算**（以国内主流模型公开定价量级估算，具体以厂商官网实时价格为准）：

| 场景 | 量级 | 月度成本量级 |
|------|------|--------------|
| 索引一次性构建 | 350 chunk × 800 token ≈ 28 万 token | < 1 元（一次性） |
| 问答 1000 次/月 | 输入 2.5k + 输出 0.6k token/次，30% 命中缓存 | 约 10-20 元 |
| 面试教练 200 场/月 | 4 轮 × (2k+0.5k) token | 约 10-15 元 |
| AI 日报 30 期/月 | 每期约 8 条 × 300 token | < 2 元 |
| **个人站典型月成本** | — | **20-50 元**（自托管加服务器费） |

> 结论：**成本不是瓶颈，滥用才是。** 限流比选便宜模型更重要。

## 十、P1 实际落地记录（2026-09-03）

> 本节记录 P1「AI 学习助手」后端的真实落地结果，与上方 6.1 节的「通用方案」不同——通用方案保留作自建参考，实际因内网网关而调整了选型。

### 10.1 实际技术选型

| 项 | 计划设想 | 实际落地 | 原因 |
|----|---------|---------|------|
| 对话 LLM | DeepSeek-chat（云） | **deepseek-v4-flash**（内网网关 `30.207.101.37:3001`） | 用户提供的内网聚合网关，多模型可用、免外网依赖 |
| Embedding | bge-m3 自托管 / bge-small | **qwen3-embedding-4b**（2560 维，内网网关） | 见 10.2，bge-m3 别名在网关路由不稳定 |
| 存储 | SQLite + sqlite-vec | **index.json（BM25）+ vectors.json（向量）** 两文件 | 350 chunk 规模下文件即够用，先不引重型向量库 |
| 检索 | BM25 + 向量 RRF | 同计划，已实现 | — |

### 10.2 关键发现：内网网关是「多模型聚合」

用户给的 `30.207.101.37:3001` 不是单一 LLM，而是一个聚合了 60+ 模型的 OpenAI 兼容网关（`/v1/models` 可枚举），含 bge-m3、qwen3-embedding-4b、qwen3-reranker-4b、bge-reranker-v2-m3、deepseek/kimi/glm/qwen 全系等。

实测稳定性：`bge-m3` 在 `/v1/embeddings` 上**间歇性 400**（6 次仅 1 次成功，网关把请求路由到不支持的渠道）；`qwen3-embedding-4b` **6/6 稳定**（2560 维）。故弃 bge 改用 qwen3-embedding-4b。后续若要提精度，可直接接网关的 `qwen3-reranker-4b` 做重排序。

### 10.3 踩坑记录（务必照此规避）

1. **代理环境变量坑（最隐蔽）**：WorkBuddy 沙盒设置了 `HTTP_PROXY=http://127.0.0.1:54233` 出口代理，它**不转发内网地址**。服务进程的 `fetch` 请求内网网关会报 `upstream connect failed (os error 10061)`。**解决**：`server.ts` 启动时 `delete process.env.HTTP_PROXY`（及大小写、ALL_PROXY 等 6 个变体）强制直连。
2. **ESM import 提升坑**：`embed.ts` 顶层 `const BASE = process.env.XXX` 会在 `loadEnvFile()` 执行前求值（import 提升），导致读不到 `.env`。**解决**：env 一律改为函数内惰性读取，不放在模块顶层。
3. **思考模型坑**：`deepseek-v4-flash` 是思考（reasoning）模型，流式先发 `reasoning_content`（英文思维链）再发 `content`。**解决**：SSE 转发时过滤「仅含 reasoning_content、无 content」的 chunk，只把正文 `content` 给前端。若想更快更省，可换 `deepseek-v4-flash-no-thinking`（改 `.env` 一行）。
4. **CORS 跨域坑**：原 CORS 白名单只认 `localhost:4322`，用户若用 `127.0.0.1:4322` 访问（host 变体）会导致 fetch 的 Origin 与 `Access-Control-Allow-Origin` 不匹配，浏览器拦截跨域请求、聊天静默失效。**解决**：`index.ts` 的 origin 回调额外放行 `localhost` / `127.0.0.1` 的任意端口（正则匹配回环地址），其余来源 `return false` 拒绝。
